The shared checkout lands work on `{lane}` directly — `{lane}` is the "shipped, pending deploy" branch (unpushed = `origin/{lane}..{lane}`); no push step is yours. The ship leg commits the story's files on `{lane}` — code AND its artifact set: `python "{project_root}/.agents/skills/cdo-platform/scripts/ship-commit.py" --project-root "{project_root}" --orchestration-dir "{orch}" --work-tree "{project_root}" --keys {{key}} --paths <the story's code paths> --require-status verified --message "cdo {{key}}: <terminal status>"` (no `--add-all` — the main tree carries unrelated dirty state; ship-commit stages the reported artifact paths plus what you name) — then mirrors the tip into `refs/heads/cdo-lane` (the org's local integration ref) — **FF-only**: `python "{project_root}/.agents/skills/cdo-platform/scripts/land.py" --project-root "{project_root}" --work-tree "{project_root}" --lane "{lane}"` — it rebases when the lane moved under you, retries the compare-and-swap once, then reports `blocked` — record it and move on, never force; `already-abreast` → the story is already on the lane — use its `ship` sha. Pass the landed sha on the shipped outcome (`dispatch.py outcome --status shipped --lane-sha <ship sha from land.py>`) so the sign-off knows exactly what to push. Verification runs BEFORE the ship leg completes — unverified code never ships. Nobody pushes to origin on this path either — the push is the Operator's pre-deploy sign-off (cdo-platform `push`).

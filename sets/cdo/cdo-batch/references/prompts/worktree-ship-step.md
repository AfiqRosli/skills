Ship = commit the story — `python "{project_root}/.agents/skills/cdo-platform/scripts/ship-commit.py" --project-root "{project_root}" --orchestration-dir "{orch}" --work-tree "{work_dir}" --keys {{key}} --add-all --require-status verified --message "cdo {{key}}: <terminal status>"` (it mirrors the story's artifacts from the MAIN checkout into your worktree — devlog, archived card, session docs, review docs, knowledge files ride the commit, not just code — stages, commits, reports the sha) — then land it: `python "{project_root}/.agents/skills/cdo-platform/scripts/land.py" --project-root "{project_root}" --work-tree "{work_dir}" --lane "{lane}"` — it lands your HEAD on `refs/heads/cdo-lane` **FF-only** (a stale base gets rebased+captured first; CAS refused → rebase+retry once, then `blocked` — never force) and advances the Operator's checkout — the local `{lane}` branch means "shipped, pending deploy" (unpushed = `origin/{lane}..{lane}`); an advance refusal surfaces in `warnings`, it does not fail the ship — the drain-end sweep heals it. `blocked` → record it and move on, never force; `already-abreast` → the story is already on the lane — use its `ship` sha. Verification runs BEFORE the commit — unverified code never lands on the lane. Never `git push` — pushing to origin is the Operator's pre-deploy sign-off (cdo-platform `push`), not yours. Pass the landed sha on the shipped outcome (`dispatch.py outcome --status shipped --lane-sha <ship sha from land.py>`) so the sign-off knows exactly what to push.
